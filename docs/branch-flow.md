# Ветки, pull request и релизы Telegravim

Основной репозиторий: <https://github.com/Informativus/telegravim>.

| Ветка | Назначение | Как попадают изменения |
| --- | --- | --- |
| `main` | Стабильные релизы; ветка по умолчанию | PR из `develop` с merge commit |
| `develop` | Разработка, интеграция и бета-версии | PR из отдельных рабочих веток |
| `feature/*`, `fix/*`, `docs/*`, `chore/*` | Одна задача | Создаются от актуальной `develop` |

Все изменения, включая документацию, зависимости, обновления upstream и работу
агентов, проходят через PR. Прямые push и force-push в `main` и `develop`
запрещены. Обе ветки защищены от удаления; правила действуют и для администраторов.
Владелец может объединить собственный PR: обязательного одобрения второго
участника нет. Перед объединением нужно завершить обсуждения и проверить diff.

## Обычная задача

Начинайте с чистого рабочего дерева. Если в нём есть чужие или незавершённые
изменения, сохраните их отдельно, не сбрасывайте ради переключения ветки.

```sh
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/short-description

# Внесите изменения и добавьте только файлы своей задачи.
git add path/to/changed-file
git commit -m "Describe the change"
git push -u origin HEAD
gh pr create --repo Informativus/telegravim --base develop
```

В PR укажите, что изменилось, как это проверено и какие проверки остались.
Используйте проверку, соразмерную изменению: для документации достаточно проверки
diff и ссылок; для поведения приложения нужны соответствующие сборка и проверки.
Объединяйте PR через GitHub с merge commit. После объединения рабочую ветку можно
удалить; `main` и `develop` остаются постоянными.

По состоянию на настройку этой схемы GitHub Actions отключены. PR и его
объединение сами по себе не запускают сборку, не создают DMG и не публикуют релиз.
Обязательные CI checks не настроены: результаты проверки записываются в PR.
Унаследованные workflow upstream нужно адаптировать до включения Actions,
включая старый `dev-to-master` updater и публикацию официальных пакетов Telegram.

## Бета-версии

Бета собирается из выбранного коммита `develop` после объединения рабочих PR.
Исправления беты тоже идут отдельной веткой через PR в `develop`.

При запросе публикации беты создайте уникальный тег на проверенном коммите
`develop`, например `2026.09.07-100-beta.1`. В GitHub Release включите
**Set as a pre-release**; бету не назначайте последним стабильным релизом.
Зафиксируйте точный коммит и приложите собранный из него артефакт.

## Стабильный релиз

1. Завершите проверку выбранной беты в `develop`. Изменение версии или release
   notes, если оно нужно, сначала проведите рабочим PR в `develop`.
2. Создайте PR `develop` -> `main` и укажите выпускаемую версию и проверки:

   ```sh
   gh pr create --repo Informativus/telegravim \
     --base main --head develop --title "Release <version>"
   ```

3. Проверьте весь diff PR и объедините его через **Create a merge commit**.
   Не используйте squash или rebase: обе постоянные ветки должны сохранять
   общую историю. Если `develop` изменилась после проверки, проверьте новый diff
   перед объединением.
4. Получите актуальную `main`. Соберите и проверьте релиз из точного коммита,
   получившегося после объединения; стабильный тег должен указывать на него.
5. Для macOS подготовьте свежий `out/Telegravim.dmg` из `Release`, выполните
   strip, подпишите bundle с `Telegram/Telegram/Telegram.entitlements` и
   проверьте `codesign --verify --deep --strict` и `hdiutil verify`.
6. Создайте стабильный тег, например `2026.09.07-100`, и обычный GitHub Release
   без признака prerelease. Прикрепите проверенный артефакт. Публикацию выполняйте
   только по запросу на релиз; документационный PR сам по себе не повод выпускать
   новую версию.

Поскольку `main` принимает изменения только из `develop` обычным merge commit,
её содержательные изменения уже есть в `develop`. Отдельный обратный merge
после каждого релиза не нужен. Опубликованные теги не перемещайте и не заменяйте
артефакт другой сборкой под тем же тегом.

Срочное исправление проходит тот же путь: `fix/*` -> `develop` -> `main`.
Релизный PR включает все накопленные изменения `develop`; если там есть
непроверенная работа, сначала согласуйте состав выпуска, не включайте её
в стабильный релиз автоматически.

## Обновление Telegram upstream

Проверяйте выбранную версию Telegram и интегрируйте её на отдельной ветке:

```sh
git fetch origin
git fetch upstream --tags --recurse-submodules
git switch -c chore/update-telegram origin/develop
git merge upstream/dev
git submodule update --init --recursive
# Разрешите конфликты, проверьте изменения и сборку.
git push -u origin HEAD
gh pr create --repo Informativus/telegravim --base develop
```

Вместо `upstream/dev` можно выбрать проверенный upstream-тег или коммит.
Не перебазируйте `main` или `develop` и не отправляйте изменения в официальный
репозиторий Telegram. Изменения собственного submodule сначала опубликуйте
в его репозитории, затем обновите указатель через PR в Telegravim.

## Remotes в локальной рабочей копии Ивана

| Remote | Адрес | Назначение |
| --- | --- | --- |
| `origin` | `https://github.com/Informativus/telegravim.git` | Рабочие ветки, PR и релизы |
| `upstream` | `https://github.com/telegramdesktop/tdesktop.git` | Получение обновлений; push URL — `DISABLED` |
| `backup` | `/Users/ivan/Documents/Projects/telegram-lite-vim.git` | Локальная резервная копия |

Локальные `main` и `develop` отслеживают одноимённые ветки `origin`.
Резервная копия обновляется вручную и не заменяет PR. После получения актуальных
веток GitHub её можно обновить командой `git push backup main develop`.
В новом клоне `origin` уже указывает на GitHub; `upstream` добавляется отдельно.

При переходе на эту схему прежняя GitHub-ветка `vim-keymap` переименована в `main`;
`main` и `develop` созданы на основе уже опубликованного релиза `2026.09.06-99`.
История сохранена. Старая локальная `dev` сохранена как `archive/upstream-dev`,
а прежняя `vim-keymap` остаётся в `backup` как историческая точка.
Старые планы с `vim-keymap`, прямым push и rebase общей ветки заменены этой схемой.
